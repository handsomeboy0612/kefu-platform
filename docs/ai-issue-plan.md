# 对公群 AI 问题识别方案

> 状态：方案待拍板，未开始开发。日期：2026-11-24。

## 1. 要解决什么

现在对公群按「30 分钟没人说话就切一段」，再用写死的规则判断归属（谁先回复算谁、派单规则、@ / 引用带走客户）。有三个毛病：

1. **一个问题被拆成好几段**：11-18 唐斌的「mimo2.6flash 报错 / 量不够」从头到尾是一个问题，被切成 4 段，「解决问题数」算多、首响算了 4 次。
2. **归属靠规则猜**：成都开心音符 11-19，涂女士 @王智 → 王智回「好的」→ 王智 @郑嘉鑫 跟进 → 郑嘉鑫实际回复客户。规则把这段算给王智，因为他的「好的」被当成了第一次回复。
3. **不知道解决没有、什么时候解决的**：所以「处理时效」（10 分）和「问题闭环率」（20 分）一直空着；「解决问题数」（35 分）实际统计的是段数。

## 2. 结论：判断交给 AI，规则只做约束和兜底

| 现在写死的规则 | 以后谁负责 |
|---|---|
| 30 分钟切段 | **AI**：判断哪些消息属于同一个问题，中间穿插别的问题也能分开，隔天的「还是不行」能接回原问题 |
| 谁先回复算谁、派单规则、@ / 引用带走客户 | **AI**：判断这个问题实际是谁处理 / 解决的，派单、「好的」这类回应同事的话自然能看懂 |
| 是否解决、在哪条消息解决 | **AI**：给出结论并引用原话作为依据 |
| 谁算数（「参与考核」勾选） | **程序**：你勾谁算谁，AI 不管这个 |
| 首响、处理时效、闭环率 | **程序**：按消息时间戳计算，不让 AI 估 |
| 内部群排除、人员挂靠 | **程序**：不变 |

~~现有的切段和规则不删，留作兜底~~ —— 2026-11-26 主管决定弃用按时间切段，不再兜底：AI 没配置、调用失败、校验不过的群·天没有结果（不算分），在「群问题」页能看到失败记录，可以重新分析。

## 3. 给 AI 的输入

**处理单位：一个群一天（北京时间）**，只处理当天客户和员工都发过言的群。按 11-16 ～ 11-24 的真实数据，每天约 25 个群、300～400 条消息、1.5 万字，单个群一天最多 77 条，一次调用完全装得下。

**消息格式**（每条带编号，AI 只能用编号引用消息）：

```
[m:3792505] 11:06 客户·唐斌：[图片]
[m:3792506] 11:06 客户·唐斌：@郑嘉鑫 这个现象还存在哈
[m:3792510] 11:22 员工·技术支持总监-王智 @技术支持部-蒋海军：跟进一下
[m:3792512] 11:23 员工·技术支持部-蒋海军：稍等
[m:3792530] 14:08 员工·技术支持部-蒋海军 ↪引用 m:3792528：这个是 self1，可以加上 self3
```

另外带上：

- **群员工名单**（群昵称 + 企微 ID），让 AI 认得「技术支持部-蒋海军」和「蒋海军」是同一个人。
- **往前带的旧问题**：这个群近 3 天「未解决 / 判断不了」的问题（编号、摘要、最后 5 条消息），以及 24 小时内刚判为「已解决」的问题，用来识别「接着问」和「复发」。

## 4. AI 的输出（JSON）

```jsonc
{
  "issues": [
    {
      "ref": "new",                      // 新问题填 new；接回旧问题填旧问题编号
      "summary": "mimo2.6flash 量不足报错，建议加 self3 分组兜底",
      "customer_ids": ["7881300760947455"],
      "message_ids": ["3792505", "3792506", "3792510", "3792512"],
      "handler_id": "1688856205778096",  // 实际处理 / 解决的员工（不限技术支持，商务也照实写）
      "handler_reason": "王智只派单，蒋海军接手排查并给出方案",
      "helper_ids": [],                   // 参与但不是主要处理的员工
      "status": "resolved",               // resolved 已解决 / unresolved 未解决 / unknown 判断不了
      "resolved_msg_id": "3792530",
      "evidence": "这个是 self1，可以加上 self3"   // 必须是原消息里的原话
    }
  ],
  "other_message_ids": ["3792540"]       // 闲聊、通知、模型上架公告等，不属于任何问题
}
```

**提示词里的判断标准：**

- **归属**：看实际处理 / 解决的人，不看谁先开口。「@某某 跟进一下」是派单，归被派的人；只回「好的」「收到」回应同事的不算处理。
- **已解决**：客户明确确认（「好了」「可以了」「跑通了」），或技术给出了实质解决办法、客户之后没再追问这个问题。
- **未解决**：客户还在反馈问题，或技术明确说暂时做不到（「这个我们现在没办法做」）。
- **判断不了**：只有「好的」「稍等」，或者关键内容只有截图。
- **复发**：客户隔一段时间回来说同一个问题（「效果还是不行」），接回原问题，状态改为未解决。

## 5. 程序校验（防 AI 出错）

AI 返回后逐项检查，不合格就重试一次，再不合格这个群当天退回规则：

1. 消息编号都真实存在，属于这个群这一天或带入的旧问题；每条消息只属于一个问题。
2. 处理人是员工，并且在这个问题里发过言或被派过单。
3. 解决消息在这个问题的消息里，时间不早于问题的第一条消息。
4. 依据原话必须能在原消息里找到，防止编造。
5. 接回旧问题时，旧问题编号必须存在。

## 6. 怎么计分

- **问题 → 会话记录**：沿用现有的会话结构（编号 = `wg_群ID_首条消息ID`），会话记录、AI 质检、看板、绩效页不用重做；另外存摘要、状态、解决时间、依据原话、归属理由。
- **计入谁**：处理人勾选了「参与考核」才计入；没勾选的不计，**也不转给别人**，并在同步结果里提醒。
- **解决问题数** = 处理人名下「已解决」的问题数（见第 12 节待定）。
- **首响** = 客户第一条提问 → 处理人第一条回复；派单那句不算（见第 12 节待定）。
- **处理时效** = 客户第一条提问 → 解决那条消息。
- **问题闭环率** = 已解决 ÷（已解决 + 未解决）；判断不了的不计入分母。
- **跨天的问题**：算在问题开始的那一天。

## 7. 结果稳定、可复核

- **缓存**：一个群一天的输入（消息 + 带入的旧问题 + 提示词版本 + 模型）没变，就不重新调 AI。同步十次结果都一样，考核数据不会自己变。
- **冻结**：一个群一天过了 2 天、带入的旧问题也没再变化，就不再重算。
- **固定模型和提示词版本**：换模型或改提示词要整批重跑，并出对比报告后再切换。
- **可复核**：会话详情显示摘要、状态、依据原话、归属理由；主管可以改归属和状态，手动改过的永远不会被覆盖。

## 8. 成本和速度

每天约 25 次调用，每次几千字；带上旧问题也只多一倍左右。用现在配置的模型，费用很低。同步一周的数据约几分钟（并发 3 个，失败自动重试）。

## 9. 上线前先验证，不直接算分

1. **影子模式**：用 11-16 起的真实数据跑一遍。AI 结果只在会话记录里展示，**不进绩效**。
2. **人工核对**：主管抽 30 个问题，核对问题边界、归属、是否解决三项。
3. **对比报告**：同一时段，规则和 AI 的段数、归属差异逐条列出。
4. 准确率达到约定标准后，再切换成按 AI 结果计分。

## 10. 局限和风险

- **截图看不到**：现在只存了「[图片]」占位，很多报错是截图。要解决需要机器人上传图片，是另一项改动。
- **AI 会错**：靠依据原话、程序校验、主管可修改兜底。
- **数据外发**：群聊内容会发给配置的 AI 接口，和现在的 AI 质检一样。
- **只在桌面端同步时运行**：不同步就不分析。以后可以挪到归档服务每晚自动跑。

## 11. 分期

| 期 | 内容 |
|---|---|
| 一期 | AI 分问题 + 归属 + 状态；程序校验、缓存、退回规则；影子模式和对比报告 |
| 二期 | 切换计分（处理时效、问题闭环率开始计分）；会话详情展示摘要和依据；主管修改归属 / 状态 |
| 三期 | 主管合并 / 拆分问题；机器人上传图片 |

## 12. 已拍板（2026-11-25）

1. **首响口径**：从客户第一条提问到处理人**第一次回应**，回「稍等」也算；只 @ 同事的派单那句不算。
2. **解决问题数**：处理人**接手的问题都算**（衡量工作量）；有没有解决由「问题闭环率」那 20 分去算，避免未解决的问题被扣两次。
3. **判断不了的问题**：列给主管确认（「群问题」页可改状态），确认前不计入闭环率。
4. **切换计分**：先影子模式（只展示）；主管核对满 30 个问题、三项（边界 / 处理人 / 是否解决）全对的比例到 90% 后，再把技术支持部第二项改成按 AI 结果计分。

## 13. 实现情况（2026-11-25，kefu-platform）

- 对公群每 10 分钟自动同步一次（最近 2 天），同步时把选中群的原始消息存进 wg_messages；每次同步成功后自动分析最近 3 天（含今天），第一次从有群消息的第一天开始。
- 当天也分析：一个群聊天停下超过 30 分钟（设置 → 对公群 → 群筛选里可改）才分析；之后又有新消息、再停下来就重新分析这个群当天。正在聊的群先不动。（2026-11-25 按主管意见从「只分析过完的天、每小时」改成这样）
- 隔天接续：分析时带上这个群近 3 天未解决 / 判断不了的问题和 24 小时内刚解决的问题，客户隔天说「还是不行」会接回原问题（11-16 ~ 11-24 有 21 个问题跨天接上）。
- 一个群一天调一次 AI（温度 0，JSON 输出），程序按第 5 节校验，不过就把错误带回去重试一次，再不过这个群当天记失败（没有结果，不算分）。
- 缓存和稳定：输入指纹 = 这天的消息 + 之前各天的结果 + 提示词版本 + 模型；没变不重调 AI。某天要重跑时，先倒序撤回这天及以后各天对问题表的改动，再按天重放（输入没变的直接用缓存结果）。同样的输入失败 3 次后不再自动重试。
- 主管的核对和修改按「群 + 问题第一条消息」存，AI 重跑也不会丢。
- 「群问题」页：每人汇总、问题列表、详情（聊天记录、解决那条消息、依据原话、归属理由）、核对三项、改处理人 / 状态、重新分析；页面顶部显示核对准确率。
- 会话记录里的对公群 = AI 群问题（2026-11-25 起，按第 9 节「AI 结果在会话记录里展示」）：一个问题一行（会话 ID = `wgi_部门_群+第一条消息的哈希`），挂在处理人（按主管改过的）名下，只挂本部门成员处理的；商务处理的、没人处理的只在「群问题」页看。分析完、主管改处理人 / 状态、员工挂靠变了、每次同步后都对一遍，内容指纹没变的不写。点开是群问题详情（可核对、可改）。群问题不做 AI 质检评分。
- 按时间切段的群会话 2026-11-26 弃用：同步不再切段，考核规则里的「数据来源」选项去掉，库里的旧群会话删掉。之前生成的绩效报表（快照）照旧能看。
- **2026-11-26 起技术支持部第二项按 AI 群问题计分**（主管要求直接列入考核，没等第 12 节约定的 30 个核对、90% 准确率）。计分按《技术支持部绩效考核标准》（2026-11-11）第三部分：
  - 解决问题数 = 处理人名下的群问题数（第 12 节决定 2），按难度加权：简单 ×1、一般 ×1.5、疑难 ×2，难度由主管在「群问题」里标，没标的按简单。处理人、状态按主管改过的算。
  - 首次响应：从商务、主管或客户 @ 处理人让他看（派单）开始算（主管 2026-11-26 定）；没人 @ 他、他自己接的，从客户这一轮提问开始算（1 分钟内连发的算一条，从最后一条算；前面已经有我方的人回过的不算）→ 处理人第一次回应（「收到，正在看」「稍等」也算，只 @ 同事的派单不算）。值班按全天有人算（主管 2026-11-26 定），不扣非值班时间。
  - 平均响应：接手后客户每一轮提问 → 处理人下一次回应的平均；别的同事先回了的那一轮不算；客户只回「好的」「谢谢」、说「我们看看」「我试试」（没在问）、发看不到内容的消息，不算提问。
  - 处理时效：从首次响应到解决那条消息，1 小时内 100%；超过 1 小时但处理人每小时至少同步一次进度（只回「稍等」「还在看」不算）70%；没同步 0。「依赖上游、按时同步得 100%」程序分不出来，需要的话主管改状态或人工调整。
  - 问题闭环率 = 各问题计分之和 ÷ 问题数：解决 1、没解决但交接完整 0.8、交接不完整 0.4（交接两档由主管在「群问题」里改状态）、没解决没交接 0；判断不了的主管确认前不算（第 12 节决定 3）。≥95% 满分、90% 得 80%、80% 得 50%、≤70% 得 0，中间线性。
  - 客户满意度、扣分项、主管评分：人工录入，和 PDF 一致。
  - 还没做的：跨班交接时交接人和解决人各记 0.5 个；「没人接手的归当班负责人」（没有值班表）。
  - 一开始（11-26 上午）处理时效和闭环率用的是我拟的分档，没对照 PDF；响应时间一度改成「只算处理人参与的对话段」。下午按 PDF 和主管意见改成上面的口径。
  - 是否解决的判断标准（提示词 issue-v3，2026-11-26）：按 PDF「客户确认，或者没有再追问」——员工给出结论（解决办法、原因说明、替代方案如「暂时没量，建议先用 xx 分组」、明确答复）之后客户没再追问，就算已解决，问题本身暂时没法彻底解决也一样；客户之后再追问会接回原问题重新判断。之前（issue-v2）「员工说暂时做不到」一律判未解决，56 个未解决里大半其实给了替代办法。改完重新分析 11-16 ~ 11-26（177 次调用、约 40 万 tokens）：已解决 122 → 169，未解决 56 → 25，判断不了 21 → 7。resolved_msg_id 改成填员工给出结论那句（处理时效按 PDF 算到「给出解决方案」）。
  - 会话记录里每个群问题显示单题分：首次响应、平均响应、处理时效、是否解决按第二项分值加权平均（0 ~ 100），只是参考，人的第二项还要看解决问题数、闭环率、满意度和扣分。
  - 每次生成报表前先把群问题对一遍，保证处理人、状态是最新的。
