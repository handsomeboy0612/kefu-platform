# 客服考核数据平台（kefu-platform）方案

> 状态：一期功能完成（2026-11-25）：登录和账号、按部门的数据源与 AI 设置、成员、SaleSmartly 每小时同步、会话记录、AI 质检、统计看板、绩效考核、对公群；已正式部署在 DESKTOP-81HRUPD（D:\kefu-platform，系统账户开机自启）。下一步：和桌面版并行对照一个考核周期。二期 AI 分问题已上线影子模式（左侧「群问题」，见 ai-issue-plan.md 第 12、13 节）；对公群的管理挪到「设置 → 对公群」。

### 对公群（2026-11-25 做完）

- 切段、按「谁实际回复了」拆分、派单识别、群昵称自动挂靠，全部从桌面版技术支持部版本原样搬过来。
- 按规则切的群会话存进 ss_sessions（source = 'wgr'，渠道 -2），只给技术支持部第二项计分，不在页面上出现。
- 会话记录、看板里的对公群是 AI 整理的群问题（source = 'wg'，一个问题一行，挂在处理人名下，只挂本部门成员处理的；2026-11-25 起）。回复率、第一项 AI 质量、出勤只算 SaleSmartly 会话（和桌面版口径一致）；群问题不做质检评分，显示按第二项规则算的单题分。
- 技术支持部第二项默认按 AI 群问题算，口径按《技术支持部绩效考核标准》第三部分（难度加权、处理时效按 1 小时 / 每小时同步进度、闭环率含交接 0.8 / 0.4），考核规则里可以切回规则群会话（2026-11-26，口径见 ai-issue-plan.md 第 13 节）。
- 每小时自动同步最近 3 天（往前多拉一天看段的开头，只存开头落在时段里的段，重复同步结果稳定）；对公群页可手动重同步。
- 对公群页：群会话、员工挂靠（可手动指定）、群筛选与切段间隔、同步记录（挂靠提醒、机器人采集中断）。
- 技术支持部绩效第二项接上：解决问题数 = 群会话数，首响 / 均响按每个群会话算再平均；处理时效、问题闭环率等二期 AI 分问题。

### AI 质检（2026-11-25 做完）

- 每个部门自己的提示词、评分维度和权重（设置 → AI 质检）。默认值：客服部 = 桌面版 main 分支的提示词，五个维度；技术支持部 = 技术支持部桌面版实际在用的提示词，六个维度（问题解决度 35、专业能力 20、服务态度 15、回应完整性 10、响应及时性 10、客户情绪变化 10）。
- 和桌面版的不同：
  - 输出格式按部门的维度生成。桌面版不管提示词怎么写，都要求 AI 按固定的五个英文维度输出，技术支持部的新标准实际没生效。
  - 总分按权重算，评级按总分算（桌面版评级用的是 AI 自己给的，可能和总分对不上）。
  - 判断「最后一条是谁发的」时跳过末尾机器人的自动提醒。2026-11 九成会话最后是这类提醒，桌面版因此大部分会话拿不到「会话结束状态」说明。
  - 只评客户说过话的会话；批量评分只评参与考核的客服。
- 单个评分、按列表筛选范围批量评分（同时 5 个，一次最多 5000 个，Key 无效等配置问题会自动停）、标记复核、每晚 01:00 自动评前一天（默认关）。
- 评级写回 SaleSmartly 标签沿用桌面版逻辑，受「AI 评分写回会话标签」开关控制（默认关）。

### 统计看板 / 绩效考核（2026-11-25 做完）

- 统计看板：会话量、客户评价、好评（4~5 星）/ 差评（1~2 星）/ 净口碑、AI 质检均分；每日会话量、每日好差评、按客服的好差评对比、AI 评级分布、按客服明细。按会话开始时间、北京时间分天。
- 绩效考核：两套规则原样从桌面版搬过来（客服部 = main 分支五项；技术支持部 = 2026-11-11 标准两大项 + 主管评分）。接待量、首响、均响、满意度取 SaleSmartly 大报表（按分配时间）；回复率、AI 质量、出勤天数、剔除用平台数据。
  - 参与考核只认平台成员表（本部门 + 参与考核 + 还在项目里）。
  - 回复率扣分剔除、差评申诉剔除、技术支持部每月人工录入（主管评分、投诉、扣分），改完自动重新计算。
  - 每次生成按「部门 + 时段」存快照（同一时段覆盖），历史报表可回看；导出 CSV。
  - 技术支持部第二项（对公群）等第 6 步接上群聊数据，现在按「不考核」处理，总分按第一项折算。
  - 去掉了桌面版的企微存档并入（平台不接企微存档）。
- 设置 → 考核规则：按部门模板生成表单，保存时校验各项合计；可恢复默认。
- 修了一个时区问题：MySQL 服务的时区还是美东时间，数据库里按天拆分（看板分天、出勤天数）会差 13 小时；现在每个连接都设成北京时间。
> 替代客服评分系统（Performance-Rating）的两个桌面版；Performance-Rating 项目保留不再改动。

## 1. 为什么做

现在客服部和技术支持部各装一个桌面版评分系统，各存各的数据。这几天遇到的问题都出在这里：

- 每台电脑各存一份数据，结果可能不一样；本地数据曾从 639 段会话变成 2 段。
- 要有人手动点「同步」才有数据；每次改动都要重新打包、到每台电脑覆盖安装。
- 对公群要接 AI 分问题，放在哪台桌面电脑上跑都不合适。
- 时区、配置每台电脑都可能不一样（之前 UTC-5 时区导致数据错开 13 小时）。

改成内网网页平台后：**一份数据、自动同步、AI 在服务端跑一次、浏览器打开就用、改一次所有人生效**。

## 3. 整体结构

```
云雾机器人 / Relayrouter 机器人 ──► 归档服务 archive-server（:8091，不变）──► MySQL wecom_archive
                                                                            ▲
SaleSmartly 接口 ◄──────────────── 数据平台 kefu-platform（:8092，新）────────┤
                                     · 定时同步、AI 质检、AI 分问题、算绩效     │
                                     · 网页（主管用浏览器打开）               └──► MySQL kefu_platform（新库）
```

- **机器人、归档服务不动**。平台从归档服务的接口拉对公群消息，和现在桌面版的方式一样。
- 新建一个数据库 `kefu_platform`，放在同一个 MySQL 里，加进每天的自动备份。
- 资源占用：平台常驻约 100～200 MB 内存，平均 CPU 不到 1%（AI 在远端接口上算）。

## 4. 部门怎么分

| | 客服部 | 技术支持部 |
|---|---|---|
| 主管账号 | 钟孟玲 | 王智 |
| 成员 | 白班 / 晚班 / 通宵班客服 | 技术支持 |
| 数据源 | SaleSmartly | SaleSmartly + 对公群 |
| 考核规则 | 五项：接待量、回复率、满意度、响应速度、AI 质量（含通宵班专用规则） | 第一项「客服接待」+ 第二项「对公群」+ 主管评分（含投诉、表扬、扣分人工录入） |
| 菜单 | 没有「对公群」相关的页面和设置 | 有 |

- **成员归属**：成员表里由管理员给每个人指定部门。默认按 SaleSmartly 分组给出建议（白班 / 晚班 / 通宵班客服 → 客服部，技术支持 → 技术支持部），可以改。商务等不属于任何部门的人不参与考核。
- **共用一份底层数据**：SaleSmartly 只拉一次，每段会话按接待的人归到他所在的部门；对公群数据只有技术支持部用。
- **各改各的**：两个部门的考核规则、AI 质检提示词、绩效快照、人工录入、剔除记录互不影响。

## 6. 功能清单

| 对公群（技术支持部） | 群会话列表；同步结果里的漏挂提醒、采集中断提示；群筛选、切段间隔、群内员工挂靠 |

## 7. 定时任务

| 时间 | 做什么 |
|---|---|
| 每小时 | 刷新成员名单；重拉最近 3 天开始的已结束会话（补上刚结束的会话和客户事后补的评价），补拉聊天记录；拉对公群消息 |
| 每晚 01:00 | AI 质检没评过分的会话；AI 分问题（前一天定稿，二期）；评级标签写回 SaleSmartly |
| ~~每天 09:00~~ | ~~日报推送到企业微信群~~（暂不做） |

- SaleSmartly 接口限速每秒 20 次（账号级，两个桌面版和内网分析工作台共用），平台只用约 8 次 / 秒，频率超限时自动退避重试。
- 实际量（2026-11）：每天约 500 段会话，客服部占绝大多数；技术支持部在 SaleSmartly 上一个月不到 100 段（主要在对公群）。
- 某个 SaleSmartly 项目第一次同步时从本月 1 号拉起；更早的数据在「会话记录 → 同步数据」里按时间段手动同步（一次最多 62 天）。
- 时间一律按北京时间，服务端写死，不依赖电脑的时区设置。

## 8. 数据表（MySQL 库 kefu_platform）

| 表 | 内容 |

## 9. 技术选型

- 服务端：Node + TypeScript（和现有评分系统同一种语言，业务逻辑可以直接搬）。
- 网页：React + Vite + Semi UI（现有页面基本照搬，把 57 个桌面端内部调用换成网页接口）。
- 部署：和归档服务一样，用 Windows 计划任务开机自启，崩溃后自动重启。
